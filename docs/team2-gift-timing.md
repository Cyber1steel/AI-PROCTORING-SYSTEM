# Team 2 - Gift: Timestamp & Timing

## 1. Role

Gift owns the timing contract that ties together the browser recording timeline, the moment a violation is detected, the incident clip boundaries, and the stored evidence metadata. The goal is not to create a second recording pipeline or replace the work of Philip, Anosi, or Victor. Gift's role is to make sure the same elapsed timeline is preserved across the whole Team 2 chain so a violation can be positioned accurately inside its incident clip.

Gift is responsible for:

- preserving the authoritative elapsed timeline created by Philip's recording manager
- validating the timing relationship between the violation event and clip boundaries
- storing the same timing values in the final incident metadata
- exposing the resulting data to the downstream admin playback workflow

Gift does not own:

- capturing video/audio
- detecting violations
- assembling incident clips
- uploading clips to storage
- redesigning the admin dashboard
- changing detection logic

## 2. Architecture position

The repository already implements the Team 2 chain as:

Philip -> Anosi -> Victor -> Gift -> Ibrahim

The actual handoff works as follows:

1. Philip's `ExamRecordingManager` creates a browser-side monotonic recording timeline using `performance.now()` and attaches `startElapsedMs` / `endElapsedMs` to each recording chunk.
2. Anosi's `IncidentClipEngine` computes the active incident window around a violation using the same elapsed timeline:
   - `eventElapsedMs`
   - `clipStartElapsedMs`
   - `clipEndElapsedMs`
3. Victor's upload layer sends the final incident Blob and the timing metadata to the Flask server.
4. Gift validates and normalizes that timing data before storing it with the clip metadata.
5. Ibrahim can read the stored metadata and use it to position the violation within the clip when building admin playback.

## 3. Authoritative timing model

The authoritative timeline is the browser recording-relative elapsed-time clock generated by Philip's recording system.

The project uses:

- `performance.now()` as the source of elapsed time
- a recording start timestamp (`recordingStartTs`)
- chunk `startElapsedMs` and `endElapsedMs`
- `getCurrentElapsedMs()` as the live recording elapsed time

This is the correct model for exam timing because it is monotonic, recorder-relative, and suitable for measuring the elapsed exam time while a user is being monitored.

This is not replaced with wall-clock timestamps or server time for the actual clip positioning calculation.

## 4. Timing fields

The repository already carries these timing values through the incident chain:

- `event_elapsed_ms` / `eventElapsedMs`: the elapsed recording time when the violation occurred
- `clip_start_elapsed_ms` / `clipStartElapsedMs`: the elapsed recording time where the incident clip begins
- `clip_end_elapsed_ms` / `clipEndElapsedMs`: the elapsed recording time where the incident clip ends
- `video_offset_ms`: the displacement inside the incident clip where the violation occurs

The required relationship is:

- `clip_start_elapsed_ms <= event_elapsed_ms <= clip_end_elapsed_ms`

The key computed value for playback is:

- `video_offset_ms = event_elapsed_ms - clip_start_elapsed_ms`

This is the number of milliseconds from the start of the stored incident clip to the violation moment.

## 5. Example timeline

Example violation at 42 seconds:

- `event_elapsed_ms = 42000`
- `clip_start_elapsed_ms = 32000`
- `clip_end_elapsed_ms = 47000`
- `video_offset_ms = 10000`

This means the violation occurred 10 seconds into the incident clip, which is exactly the value Ibrahim can use to seek the admin playback to the violation time.

## 6. Multiple violations

The repository's existing `IncidentClipEngine` intentionally keeps the active incident open and extends it if a second violation occurs before the current incident closes.

Gift's validation preserves that behavior by checking the invariant only after values are finalized. If the active incident is extended, the final values remain internally consistent:

- the earliest relevant `clip_start_elapsed_ms` is kept
- the latest relevant `clip_end_elapsed_ms` is kept
- the current violation's `event_elapsed_ms` is preserved
- the final incident still obeys the ordering rules

There is no separate timing state for each individual violation in the final uploaded metadata. The existing architecture keeps the single incident clip and one set of final timing values.

## 7. Beginning/end edge cases

Gift handles the required edge cases:

- Early violations near the beginning of the recording: `clip_start_elapsed_ms` is clamped to `0` instead of becoming negative.
- Exam ending before the full post-event window: the metadata reflects the actual recording window, not a made-up future time.
- Invalid ordering: if the data implies that the violation happens before the clip starts or after the clip ends, the server rejects the metadata rather than persisting a broken timeline.

Example early case:

- violation = 3,000 ms
- clip_start is computed as `max(0, 3000 - 10000) = 0`
- `video_offset_ms = 3000 - 0 = 3000`

This keeps the incident metadata logically valid.

## 8. Client/server timestamps

The project distinguishes clearly between:

- browser recording-relative elapsed time (`performance.now()` based) for the actual incident position inside the video
- server/database timestamps (`created_at`, `timestamp`) for audit/storage bookkeeping

The browser generated recording timeline is the authoritative source for incident positioning. Server timestamps are useful for metadata and audit history, but they are not used as the incident's playback position.

## 9. Integration

Gift integrates with the existing architecture by preserving the timing contract already used by Philip and Anosi and by storing it alongside the uploaded incident clip.

The project stores a JSON sidecar beside each incident clip in the same storage area. It includes:

- `event_elapsed_ms`
- `clip_start_elapsed_ms`
- `clip_end_elapsed_ms`
- `video_offset_ms`
- `mime_type`
- `created_at`

When the admin review API loads a violation, it reads the clip metadata file and exposes those values to the downstream playback workflow. Ibrahim can then use:

- the stored clip path
- the `event_elapsed_ms`
- the `clip_start_elapsed_ms`
- the `video_offset_ms`

to position the clip at the exact point of violation inside the incident footage.
