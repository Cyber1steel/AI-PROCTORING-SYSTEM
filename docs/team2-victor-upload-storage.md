# Team 2 - Victor: Upload, Storage & Backend Engineer

This component completes the handoff from the incident clip generated by Anosi to a safe, persisted file in the Flask application. It does not replace Philip’s recording layer, and it does not redesign the incident engine. Instead, Victor owns the browser-side upload and the server-side persistence contract that makes the final incident video usable by Ibrahim for later admin playback.

## Files changed

Exact files changed for this role:

- `templates/index.html`
  - Added the actual browser-side upload of the finalized incident Blob to the Flask upload endpoint.
- `routes/proctor.py`
  - Added validation, safe file naming, storage, metadata persistence, and response handling for uploaded incident clips.
- `docs/team2-victor-upload-storage.md`
  - Documented the Victor upload/storage contract and integration details.

## 1. Victor’s responsibility

Victor owns:

- receiving the finalized incident Blob from Anosi
- creating the multipart upload request from the browser
- sending the video to the Flask server
- validating the uploaded file
- generating a safe unique filename on the server
- persisting the clip to the project’s static storage area
- saving the associated violation metadata
- returning enough information for Ibrahim to later display the clip

Victor does not own:

- continuous recording and chunk buffering (Philip)
- clip assembly and selection logic (Anosi)
- admin playback UI (Ibrahim)
- authoritative time synchronization (Gift)

## 2. Architecture

Philip -> Anosi -> Victor -> Flask -> Storage -> Database -> Ibrahim

The intended flow is:

1. Philip records a rolling WebM buffer in the browser.
2. Anosi selects the relevant pre/post-event chunks and creates one incident Blob.
3. Victor sends that Blob to the Flask upload route.
4. Flask validates and stores the video in the project’s static clip directory.
5. The application records the clip path and timing metadata against the parent violation.
6. Ibrahim later uses the stored clip path to show the evidence to the admin.

## 3. Interface between Philip, Anosi, and Victor

The final incident object created by Anosi is a clean handoff payload that includes:

- violationId
- eventType
- eventElapsedMs
- clipStartElapsedMs
- clipEndElapsedMs
- blob
- mimeType
- createdAtMs

The browser receives this object and transforms it into a FormData upload with fields including:

- clip
- mime_type
- event_elapsed_ms
- clip_start_elapsed_ms
- clip_end_elapsed_ms

This contract preserves the timing information created by Philip and Anosi without adding a second recording system.

## 4. Upload mechanism

The browser creates a FormData payload in the exam page and uploads it to the existing Flask endpoint for clip storage.

The request is sent to:

- /api/proctor/upload-clip/<violation_id>

It carries:

- the file itself as `clip`
- the browser MIME type as `mime_type`
- the violation event timestamp (`event_elapsed_ms`)
- clip start and end values (`clip_start_elapsed_ms`, `clip_end_elapsed_ms`)

This is the correct Victor responsibility: one incident clip upload per violation, not continuous chunk upload.

## 5. Storage strategy

The server stores incident videos in:

- static/violation_clips/

This matches the project’s existing architecture and avoids introducing a separate external storage system.

The server generates a safe filename that includes:

- violation ID
- event type
- unique identifier
- appropriate extension (
  .webm for WebM recordings,
  .mp4 if the original MIME indicates MP4)

The stored file path is then written back to the parent violation record as `clip_path`.

## 6. Database handling

The project already used a `Violation` model with a `clip_path` field. Victor reuses that field instead of creating a new incident video table or a second video path column.

The storage routine updates the existing violation entry and commits it once the file is stored successfully.

The backend response includes the stored clip path and the timing metadata so the admin layer can retrieve it later.

## 7. Timing preservation

Victor preserves the values already provided by Philip and Anosi:

- eventElapsedMs
- clipStartElapsedMs
- clipEndElapsedMs

The server reads those values from the multipart form. It then stores them in a JSON metadata file beside the clip and returns them in the HTTP response.

This ensures the incident evidence remains tied to the original exam timeline instead of being replaced by the current server time.

## 8. Error handling

The storage route handles the following failure cases:

- missing upload file
- empty upload file
- invalid MIME type
- empty or invalid violation ID
- failed file write
- failed database commit
- invalid metadata values

The route returns HTTP 400 or 500 responses with useful JSON errors rather than silently pretending the upload succeeded.

## 9. Duplicate handling

The application avoids duplicate incident clip generation in the incident engine and does not re-upload a violation once the clip has already been finalized. The upload route still enforces a single file save per violation ID, backed by the unique filename strategy.

## 10. Snapshot compatibility

Snapshots remain in:

- static/violation_snapshots/

The incident video file is stored separately and the violation table still keeps the snapshot path. This preserves the original evidence model and allows the admin dashboard to show both the still snapshot and the video clip.

## 11. Ibrahim handoff

The backend exposes enough information for Ibrahim to later build the admin review UI. The important contract is:

- violation ID
- stored clip path
- timing values
- MIME type

Ibrahim can later render the clip with an HTML5 video element using the persisted clip path from the database or API response.
